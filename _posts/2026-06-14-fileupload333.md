### 시도 2. SUID 파일 이용하기
SUID 붙은 파일들은 거의 다 기본 시스템 파일로 건드릴 수가 없었음. 이게 뭔데 SUID지... 싶은 파일이 있으면 GTFOBins에서 찾아 그대로 적용하면 된다는데, 그런 파일은 없었네용<br><br>

그런데 `/usr/bin/pkexec`에 SUID 비트가 붙어있었음. CVE-2021-4034(PwnKit)이라는 polkit pkexec 바이너리의 메모리 취약점을 써먹을 수 있을까 싶었는데, 패치 안 된 버전이어야 바로 root까지 가는 익스플로잇이 통한다고 함. 버전만 봐서는 이게 패치가 된 상태인건지??? 숫자가 한 끗 차이로 애매해서 일단 공개된 방법으로 익스플로잇 시도했는데, 역시나 이미 패치되어 있었음. 하긴 5년 전 취약점인데..ㅜ 자동 보안 업데이트 됐겠지...<br><br>

#### CVE-2021-4034 (PwnKit) 정리

- pkexec는 SUID root 바이너리라 실행되는 순간 root 권한으로 동작함. 정상적으론 polkit 정책을 확인해서 권한 있는 사용자만 명령을 실행하게 해주는 도구.
- 취약점은 인자 처리 버그. C 프로그램은 실행 시 argc(인자 개수)와 argv(인자 배열)를 받는데, argv[0]에 프로그램 이름이 들어가므로 정상적으론 argc가 최소 1이어야 함. pkexec는 argc=0인 경우를 처리하지 않았음.
- 공격자가 execve()로 argc=0을 강제 호출하면, pkexec 내부 코드가 배열 범위를 벗어나 환경변수 영역을 argv로 잘못 읽음. 이때 환경변수를 교묘하게 세팅해두면 pkexec가 root 권한으로 공격자가 심어둔 코드를 실행 → root 쉘 획득.
- 줄을 서는데 "0번 손님"이라는 존재하지 않는 번호를 부르니 시스템이 혼란스러워져서 옆에 있던 아무나(공격자가 심어둔 것) 들여보내는 느낌...
- 메모리 손상이 아닌 로직 버그라서 익스플로잇이 안정적이고 거의 모든 배포판에 통했음. 2021년 1월에 공개되며 크게 이슈가 됐던 취약점.

#### 뜬금없는 삽질 시작... 파일시스템 오해

LinPEAS는 잘 돌아갔고, 따로 /tmp에 결과를 파일로 저장까지 잘 된 걸 확인했는데... 뭔가 이상한거...

리버스쉘 띄워놓은 칼리에서는 /tmp에 linpeas.txt 생성된거 보이는데??

확인차 실제 웹 서버(노트북)에서 /tmp를 확인해보니 linpeas.txt 가 없는것임...


왜 없는건데 싶어서 시간 동기화?? 칼리에서 /tmp에 파일 생성된 시간보다 노트북 서버 시간이 느린가..? 뭐 그런 문젠가 싶어 확인해보니 그런 것도 아니었고... 그니까 캐시 지연 같은 개념은 아니었다.


파일이 실제로는 안 만들어졌나? 싶어서 ls -al로 확인해보니 inode까지 찍힌 실제 txt 파일이 만들어져 있었고.. 읽을 수 있었고...

아 설마??? 리버스쉘이 붙은 머신이 다른 머신인건지...... 뭐 둘다 vm에서 돌아가는거니까... 엥 근데 그럴 수가 있나?? 참고로 도커도 안 쓴 환경임. 실제로 칼리 리버스 쉘과 타겟 서버 쉘 양쪽에

```
cat /etc/machine-id
```
해보니 같은 머신 아이디가 떴음. 리버스쉘이 웹 서버 가동중인 머신에 잘 달라붙은 게 맞았음.



그 다음으로 /tmp의 아이노드를 대조해 봄. 여기서 타겟과 칼리가 다른 결과가 뜸.

```
ls -lid /tmp
```

타겟에서 직접 /tmp의 아이노드를 보면 2359297이 뜨고,<br>
리버스쉘에서 보면 /tmp의 아이노드가 2359306으로 떴다!

그니까 두 /tmp가 다른 디렉터리라는 건데... 왜...?ㅜㅜ 열심히 클로드에게 물어봤고

양쪽의 mount namespace가 달라서 그렇다고 한다.

```
readlink /proc/self/ns/mnt
```
를 양쪽에서 실행했을 때, namespace ID가 다르게 떠서 리버스쉘로 딴 계정(www-data)과 실제 웹 서버에서 돌린 계정(jin)이 다른 mount namespace에 있었음... 잉

![mnt](/assets/img/260614/f11.png)
*칼리 리버스쉘 www-data 계정*

![mnt](/assets/img/260614/f12.png)
*타겟 jin 계정*


알고봤더니 www-data 쉘에서 
```
cat /proc/self/mountinfo | grep -i tmp
```
의 결과로,<br>

```
.../tmp/systemd-private-d278abdb...-apache2.service-0GdLfs/tmp /tmp ...
.../var/tmp/systemd-private-d278abdb...-apache2.service-Fs2AWN/tmp /var/tmp ...
```
<br>
로 떠서... 아파치 자체가 systemd의 PrivateTmp=true로 격리 실행하고 있었던 거였다.<br><br>


정리하면:

- 아파치(웹서비스)가 PrivateTmp=true로 실행됨
- 그래서 아파치와 거기서 파생된 www-data 프로세스는 자기만의 - 격리된 /tmp를 봄 (실제 위치는 /tmp/systemd-private-...-apache2.service-.../tmp)
- 일반 로그인한 jin은 진짜 /tmp를 봄
- LinPEAS를 www-data로 돌렸으니 linpeas.txt는 격리된 /tmp에 생겼고, jin이 진짜 /tmp를 봤을 땐 당연히 없었던 것이었다.

<br>
결론은 /tmp는 격리된 환경이니 LinPEAS로 나온 것 중 /tmp 관련된 게 있으면 진짜 시스템상의 /tmp는 아니니까 약간 걸러봐야 하고...

아파치 자체에서 privatetmp를 해놓는 걸 몰랐다. 생각해보니 그래놔야 /tmp를 통한 공격이 축소화될거니까... 합리적이고 당연한 보안 설정이었다.
